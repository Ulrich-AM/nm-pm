View-Dependent 2D Sprite Projection for 3D Articulated Motion

A living technical study of how mathematically three-dimensional orientation can be represented at runtime using stored two-dimensional sprite views, geometric transformation, interpolation, and later depth-aware articulated composition.

The basic research pipeline is working end to end:

PoseKnown 3D orientation
CaptureStored 2D view bank
SelectYaw and pitch neighbors
RebuildTransform or blend sprites
MeasureCompare to true projection

Phase 5 freezes the Phase 4 reconstruction methods and applies them to four new adversarial rigid subjects. A2 targets protrusions, A3 targets thin structure, A4 targets concavity and negative space, and A5 targets self-occlusion. E5 compares all six methods across A1-A5 without retuning the original formulas.

Research Problem

Given a known 3D object pose and camera pose, determine how accurately, smoothly, and efficiently the projected appearance of a rigid or articulated object can be approximated using a finite set of 2D sprite views plus screen-space transformations and depth-aware composition.

This is not a computer-vision problem. The pose is already known mathematically. The uncertainty lies in how much visual information must be stored and how well intermediate orientations can be reconstructed.

Coordinate Model

  • +X points right.
  • +Y points up.
  • +Z points toward the default camera.
  • The camera looks along -Z.
  • The system is right-handed.
  • Human-facing rotation order is yaw, then pitch, then roll.
vscreen = Portho(Rroll Rpitch Ryaw v)

Orthographic projection intentionally removes Z from screen X and Y. Depth is still retained internally for ordering and later articulation work.

Subjects

C0

C0 is the permanent unit-cube calibration subject. It is used to expose sign errors, anchor wrap problems, and projection mistakes before more ambiguous geometry is introduced.

A1-r1

A1 is deliberately asymmetric so directional errors cannot hide behind cube symmetry.

Phase 5 stress set

SubjectStress targetReason
A2ProtrusionsLong off-center appendages and a depth-facing spur amplify view-dependent silhouette changes.
A3Thin structureNarrow rods and slabs expose disappearing features, boundary error, and blending instability.
A4ConcavityA U-shaped negative-space opening tests whether reconstruction preserves holes and concave silhouettes.
A5OcclusionFront and rear components at different depths force visibility changes through rotation.
A1 remains the frozen design subject. A2-A5 are not used to retune the existing methods before E5 is measured.

Orientation Bank

The current bank contains eight yaw columns and five pitch rows:

Yaw:   0, 45, 90, 135, 180, 225, 270, 315 degrees
Pitch: -60, -30, 0, +30, +60 degrees
Roll:  not captured

This produces 40 stored 128 x 128 captures for each subject. Captures are exported as PNG files, then loaded back from disk before being used by the approximation view. That separation prevents the runtime sprite side from silently reusing live reference geometry.

Reconstruction Methods

MethodCurrent role
NEARNearest stored yaw and pitch view. This is the discrete baseline.
STRETCHResidual-yaw-driven scale correction.
SHEARHorizontal strip shear driven by yaw residual.
AFFINECombined scale, shear, and translation.
DUALBlend two neighboring yaw captures according to angular position.
GRID4Blend four surrounding yaw x pitch captures.
The original Phase 2 formulas remain frozen during later evaluation. A new method does not get to redefine its baseline after seeing the results.

Roll Policy

Roll is currently applied as ordinary 2D screen rotation after yaw and pitch reconstruction. It does not have its own sprite-bank dimension. Phase 4 includes a dedicated roll check so this assumption can be rejected later if the evidence does not support it.

Measurements

The quantitative evaluator currently records:

  • silhouette intersection-over-union;
  • symmetric boundary error in pixels;
  • centroid displacement in pixels;
  • requested orientation, selected views, and residual angles.

E5 extends the same measurements across A1-A5 and reports each method's mean IoU change relative to A1. No universal pass/fail threshold is imposed before measurement. Numerical findings are not written into this notebook until the corresponding native export has actually been executed and reviewed.

Visual Evidence

SP-REF-001 - Orientation-grid reference

User-provided reference showing directional images arranged across two orientation axes. It informed the current yaw x pitch contact-sheet structure.

SP-FAIL-001 - Blank approximation viewport

Phase 2.1 screenshot showed loaded anchor thumbnails while the large approximation view remained blank. This isolated the problem to the custom low-level sprite renderer.

SP-UI-001 - Oversized Phase 4 window

The 1600 x 980 default window exceeded usable desktop height. Build 1.6.1 reduced the default to 1360 x 820 while keeping high-resolution capture and font resources.

When visual behavior cannot be understood reliably from text, screenshots or recordings should be collected instead of guessed from descriptions.

Failed Approaches

Custom large-view textured quad

The anchor thumbnails rendered correctly while the main approximation viewport stayed blank. The custom low-level path was removed and replaced with ordinary raylib texture drawing plus strip-based deformation.

Always-visible reference ghost

A smoothly rotating diagnostic reference underneath the sprite made discrete view switching look artificially smooth. It is now optional and disabled by default.

Oversized readability pass

Increasing the whole window size improved apparent readability but hid normal window controls on the target desktop. Quality improvements now come from source resolution, high-DPI rendering, and font rasterization rather than a larger default window.

Promotion Rule

A technique cannot enter the eventual reusable reference implementation in the same experiment that invents it. Promotion requires:

  1. a procedural or mathematical definition;
  2. evidence that it beats or usefully complements a frozen baseline;
  3. testing on a second object not used to design it;
  4. characterized failure conditions;
  5. reproducible parameters;
  6. no frame-specific manual tuning;
  7. a documented fallback.

Current Implementation

1. Read camera-relative yaw, pitch, and roll.
2. Locate surrounding yaw columns.
3. Locate nearest or surrounding pitch rows.
4. Select a reconstruction method.
5. Read only frozen disk-backed sprite captures.
6. Reconstruct yaw and pitch appearance.
7. Apply roll as screen-space 2D rotation.
8. Draw at the projected screen position and depth.
9. When requested, compare against the reference projection.
10. For E5, repeat the frozen pipeline across A1-A5.
11. Export per-orientation metrics and cross-subject summaries for later review.

The native harness targets C++20 and raylib 6.2. Research-specific coordinate math, bank selection, reconstruction logic, and evaluation metrics remain project code rather than raylib 3D functionality.

Limitations

  • The pitch bank currently clamps outside +/-60 degrees.
  • GRID4 can ghost when visibility changes strongly between stored views.
  • Perspective projection is outside the current experimental baseline.
  • Phase 5 remains intentionally rigid. Joints, pivots, multi-part depth ordering, and articulated sprite composition are deferred to Phase 6.
  • Phase 3, Phase 4, and Phase 5 numerical findings still require native execution and review.
  • No reconstruction method has yet passed the promotion rule.
