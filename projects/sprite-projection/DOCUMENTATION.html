View-Dependent 2D Sprite Projection for 3D Articulated Motion

Living technical notebook for representing mathematically three-dimensional orientation using stored two-dimensional view captures, geometric correction, interpolation, and depth-aware composition.

STATUS: PHASE 4 STABILIZEDINTERNAL BUILD: 1.6.1REPOSITORY-INTEGRATEDUPDATED: 2026-10-18

Overview

The study asks how accurately, smoothly, and efficiently the projected appearance of a rigid or articulated object can be approximated from a finite set of two-dimensional raster views when the true three-dimensional pose and camera pose are already known.

This is not a computer-vision problem. The underlying object orientation is known mathematically. The runtime renderer chooses and transforms stored sprite views to approximate the expected projection.

Documentation ruleMeasurements are not written as findings until the native experiment has actually been executed. Failed approaches, visual bugs, and superseded hypotheses remain in the record.

NM-PM Context

This study belongs to NM-PM, New Methodology, Powered by Machines, a monorepo of independent technical experiments developed through human-directed research with substantial generative-AI assistance.

Canonical repository: Ulrich-AM/nm-pm. Canonical study path: projects/sprite-projection/.

The project remains application-independent. Other NM-PM studies may explore blood simulation, procedural locomotion, physical human reactions, persistent surface mapping, and later topics.

Release Model

Internal harness versions and NM-PM milestone releases are separate concepts. The current native harness remains build 1.6.1. Future stable project tags use forms such as sprite-projection-v0.1.0.

Ordinary source changes trigger the project CI workflow. Deliberately pushing a matching release tag triggers a separate Windows workflow that builds Release, runs the test suite, packages the executable with documentation and disclosure, and creates the GitHub Release.

Release policyGitHub Releases represent useful checkpoints, not every experiment. The repository branch and this notebook remain the canonical research history.

Coordinate Model

  • +X points right.
  • +Y points up.
  • +Z points toward the default camera.
  • The camera looks along -Z.
  • The system is right-handed.
  • Rotation order is yaw, then pitch, then roll.
vscreen = Portho(Rroll Rpitch Ryaw v)

Orthographic projection intentionally ignores camera-space Z for screen X and Y. Z remains available for future depth ordering.

Subjects

C0

C0 is the permanent unit-cube calibration subject. It verifies coordinate signs, anchor indexing, angle wrapping, and basic projection behavior.

A1-r1

A1 is deliberately asymmetric so directional errors cannot hide behind cube symmetry. It consists of a core cuboid, raised top cuboid, and offset arm cuboid.

CORE center=( 0.00, 0.00, 0.00) half=(0.82,0.54,0.34)
TOP  center=( 0.36, 0.73, 0.08) half=(0.32,0.24,0.18)
ARM  center=(-0.93,-0.18,-0.06) half=(0.27,0.21,0.20)

Orientation Bank

The current capture bank uses eight yaw columns and five pitch rows.

Yaw:   0, 45, 90, 135, 180, 225, 270, 315 degrees
Pitch: -60, -30, 0, +30, +60 degrees
Roll:  not captured

This creates 40 stored 128 x 128 captures per subject. Captures are written to PNG files, then reloaded from disk before the sprite approximation uses them. This deliberately separates the reference renderer from the runtime sprite representation.

Reconstruction Methods

MethodDescription
NEARSelect the nearest stored yaw and pitch view without residual correction.
STRETCHHeuristic scale correction driven by yaw residual.
SHEARStrip-based horizontal shear driven by yaw residual.
AFFINECombined scale, shear, and translation.
DUALBlend neighboring yaw sprites according to angular position.
GRID4Blend four surrounding yaw x pitch samples.

The Phase 2 NEAR, STRETCH, SHEAR, and AFFINE formulas remain frozen during later comparisons so later methods do not quietly redefine the baseline.

Roll Policy

Roll is reconstructed after yaw and pitch as ordinary two-dimensional screen rotation. It does not receive its own capture dimension. Phase 4 includes a dedicated roll check so this assumption can be rejected if the measured result is inadequate.

Measurement

Current quantitative evaluation records:

  • silhouette intersection-over-union;
  • symmetric boundary error in pixels;
  • centroid displacement in pixels;
  • requested orientation, selected anchors, and residual angles.

E3 sweeps all yaw angles. E4 samples yaw and pitch and separately checks roll. Numerical conclusions remain pending until native experiment exports are produced and reviewed.

Failed Approaches

Custom low-level textured quad. The large sprite view failed while the same disk PNGs rendered normally in the anchor thumbnails. The custom path was removed in favor of ordinary raylib texture drawing and strip-based deformation.

Always-visible reference ghost. A smoothly rotating diagnostic ghost made discrete sprite switching appear smoother than it actually was. The ghost is now optional and disabled by default.

Mistaken external A1 sprite sheet. An early supplied sheet was later identified as C0 material and was excluded from the A1 experimental baseline.

Oversized quality pass. Increasing the whole application window improved apparent readability but made normal window controls inaccessible. Quality improvements now come from source resolution, high-DPI rendering, and font rasterization instead of larger default dimensions.

Promotion Rule

A technique cannot enter the eventual reusable reference implementation in the same experiment that invents it. Promotion requires independent confirmation:

  1. the method is defined procedurally or mathematically;
  2. it beats or usefully complements a frozen baseline;
  3. it is tested on a second object not used to design it;
  4. failure conditions are characterized;
  5. parameters are reproducible;
  6. no frame-specific manual tuning is required;
  7. a fallback is documented.

Current Algorithm

1. Read camera-relative yaw, pitch, and roll.
2. Locate surrounding yaw columns.
3. Locate nearest or surrounding pitch rows.
4. Select a reconstruction method.
5. Use only frozen disk-backed sprite captures.
6. Reconstruct yaw/pitch appearance.
7. Apply roll as 2D screen rotation.
8. Draw at the projected screen position and depth.
9. When requested, compare against the reference projection and export metrics.

Build and Validation

The harness targets C++20 and raylib 6.2. On Windows:

build_windows.bat
run_windows.bat

The build script configures CMake, compiles the Release target, runs the test suite, and launches the application. The current non-UI suite contains 16 tests covering coordinate conventions, yaw anchors, silhouette metrics, and pitch-grid interpolation.

The monorepo also includes GitHub Actions CI for ordinary source changes and a separate tag-triggered release workflow.

Limitations

  • The pitch bank clamps outside +/-60 degrees.
  • GRID4 can ghost when visibility changes strongly between source views.
  • Perspective projection is outside the current experiment.
  • Only rigid subjects have been evaluated so far.
  • Phase 3 and Phase 4 quantitative findings are pending native execution and review.
  • The light application chrome remains an interface experiment. The NM-PM documentation house style remains dark grayscale.
  • No reconstruction method has yet passed the promotion rule for the final reference implementation.
