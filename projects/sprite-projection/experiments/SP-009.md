# SP-009 - Animation-Driven Simplified Body Reconstruction

**Phase:** 8  
**Harness build:** 2.0.0  
**Status:** Implemented, native visual and quantitative results pending

## Question

Can the directional-sprite reconstruction system remain coherent when a complete simplified body is driven by time-varying skeletal animation rather than hand-authored test poses?

## Animation-source policy

SP-009 separates animation input from sprite reconstruction.

The runtime pipeline is:

```text
FBX animation
    ↓
Assimp skeleton/animation import
    ↓
joint mapping
    ↓
NM-PM fixed-proportion body retarget
    ↓
per-part 3D poses
    ↓
directional sprite reconstruction
```

The FBX mesh is not used as the rendered approximation.

The imported animation contributes joint directions and temporal motion. Body proportions remain fixed by the NM-PM simplified rig so every source animation is evaluated against the same research subject.

## FBX importer

Phase 8 uses Assimp 6.0.5 for FBX animation import.

The importer:

- reads the first animation clip;
- samples it at 30 FPS;
- maps a required humanoid joint set through bone-name aliases;
- supports common Mixamo-style names and generic left/right arm/leg naming;
- converts the source coordinate basis into the NM-PM right/up/forward basis;
- retargets joint directions onto fixed body lengths;
- reports missing required joints instead of fabricating them.

A deterministic built-in walk-style clip remains available when no FBX is present.

## Simplified body

The body contains ten rendered parts:

- torso;
- head;
- left upper arm;
- left forearm;
- right upper arm;
- right forearm;
- left thigh;
- left shin;
- right thigh;
- right shin.

Symmetric left/right limbs share directional sprite banks.

Six unique 40-view banks are therefore required:

- torso;
- head;
- upper arm;
- forearm;
- thigh;
- shin.

This gives 240 stored directional sprites instead of 400 separate left/right captures.

## FBX loading workflow

The Phase 8 executable supports:

1. automatic startup loading from `assets/body_rig/input.fbx`;
2. fallback startup loading from `input.fbx` or `body.fbx` in the project directory;
3. drag-and-drop of an FBX file into the running application;
4. a built-in deterministic motion clip when no valid FBX is loaded.

The executable remains usable without an external asset.

## Reconstruction

Each body part is converted into a mathematically known 3D segment pose.

The existing shared methods are reused without body-specific copies:

- NEAR
- STRETCH
- SHEAR
- AFFINE
- DUAL
- GRID4

Each part sprite is pivot-registered at its proximal joint.

Complete part sprites are currently sorted by part-center Z before composition.

## E8 protocol

E8 evaluates the active animation source.

Temporal sampling:

- 18 evenly spaced animation samples.

View sampling:

- yaw: 0, 90, 180, 270 degrees;
- pitch: -20, 0, +20 degrees;
- roll: 0 degrees.

This produces 216 body poses.

Every pose is evaluated with all six reconstruction methods.

Metrics:

- silhouette IoU;
- symmetric boundary error;
- centroid displacement.

Outputs:

- `results/phase8/E8_body_animation_metrics.csv`
- `results/phase8/E8_body_animation_summary.csv`

The export records whether the source was the built-in clip or an imported FBX.

## Controlled limitations

SP-009 intentionally does not:

- render the FBX mesh;
- infer joint locations from images;
- preserve arbitrary source-body proportions;
- model fingers, feet, facial parts, or clothing;
- preserve bone twist independently from segment direction;
- solve per-pixel depth inside a sprite.

These are kept outside the experiment so the study can isolate whether multi-part directional sprites survive realistic time-varying motion.

## Promotion relevance

SP-009 is the full-body generalization checkpoint before the final reference implementation.

A reconstruction method should not be promoted merely because it performs well on rigid objects or short chains.

## Next phase

Phase 9 should stop expanding the research subject and consolidate the evidence from SP-001 through SP-009 into a reusable reference implementation, documented fallbacks, API boundaries, and explicit failure conditions.
